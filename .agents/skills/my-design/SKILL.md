# My Design

사용자가 실제로 보고 판단하고 행동하려는 일을 중심으로 화면을 만든다. 회사명 자체를 스타일 목표로 삼지 않는다.

사용자 취향(UDP-03·06): 실제 서비스 화면을 기반으로 쌓은 뒤 변형하고, 정보·조작을 압축해 핵심 판단에 집중한다. 선례의 구체성이 구현에서 사라지거나 요구 누적으로 정보량이 커지는 문제를 줄이려는 기준이다.

## 실행 계약

### 원하는 상태

사용자가 핵심 정보를 이해하고 판단·행동할 수 있는 일관된 UI를 만들며, 선택한
디자인 원칙이 구현과 검증 결과까지 이어지게 합니다.

### 허용 범위

정보 구조·상호작용·표현을 조사·설계·구현하고, 관련 source와 사용자 피드백에서
현재 작업에 활용할 기반과 재사용 가능한 원칙을 추출할 수 있습니다.

### 실행 전제

화면 목적, 사용자 판단 질문, 핵심 행동, workspace/write set과 완료 기준을 먼저
정렬합니다.

### 구조 검증

기능·반응형·접근성·시각 품질을 실제 화면에서 확인하고, 외부 근거와 사용자
피드백의 강도를 구분합니다.

### 잔여 금지

현재 목적·조건과 무관한 회사 모사, 근거 없는 트렌드 채택, 작동하지 않는 mock과
검증되지 않은 완료 주장은 디자인 경계 밖입니다. 근거 있는 선례의 구조·세부 활용은 허용합니다.

### 출력 후 검사

핵심 행동·정보 순서·상태·오류·반응형·접근성이 목적과 완료 기준에 맞는지 다시
확인합니다.

## 책임

- 화면의 목적, 사용자의 판단 질문, 핵심 행동을 정렬한다.
- 정보 구조, 시선 순서, 상태, 상호작용과 표현을 설계하거나 검토한다.
- 필요할 때 실제 제품 화면과 실험 자료를 근거로 사용하되 강도를 구분한다.
- 사용자 피드백에서 반복 가능한 판단 기준을 추출한다.
- 구현 전후의 기능·반응형·접근성·시각 품질을 확인한다.

브라우저, 이미지 생성, 코드 구현 같은 도구 사용법은 해당 실행 Skill에 맡긴다. 이 Skill은 그 위에서 사용자의 디자인 판단 기준을 제공한다.

## 작업 흐름

1. **판단 과제 고정**
   - 누가 어떤 상황에서 무엇을 보고 무엇을 결정하거나 실행해야 하는지 정한다.
   - 화면 종류, 플랫폼, 주요 행동, 위험과 필수 상태를 확인한다.
   - 기존 화면을 바꾸는 작업이면 현재 기능과 핵심 사용 시나리오를 먼저 목록화해 회귀 기준으로 고정한다.
2. **관련 원칙 선택**
   - `references/user-principles.md`를 먼저 읽고 현재 화면에 맞는 확정 원칙만 적용한다.
   - 일반 설계 기준이 더 필요할 때 `references/principles.md`를 읽는다.
   - 모든 화면에 같은 밀도, 카드, 색, 레이아웃을 강제하지 않는다.
3. **조사 요청과 선례 선택**
   - `references/research.md`에 따라 화면 목적과 재구현에 필요한 조사 상세를 정하고 my-precedent-research에 조사를 요청한다. 조사 결과의 충분성 판단, 사용자에게 제시할 활용안과 디자인 선택은 my-design이 맡는다. 필요한 상세가 부족하면 추가 조사를 요청한다.
   - 사용자 취향(UDP-03): 새 화면·큰 개편은 구현 전에 여러 실제 선례 화면을 시각적으로 제시하고, 주된 기반·가져올 요소·변경 방향과 추천 이유를 사용자에게 확인받는다. 이미 확정한 기반과 변경 범위는 재사용하며 작은 후속 수정에 같은 선택을 반복 요구하지 않는다. 근거와 적용 경계는 `references/user-principles.md`를 따른다.
4. **압축·설계·구현 또는 검토**
   - 사용자 취향(UDP-06): 구현 전에 요구사항과 기존 요소를 판단 목적에 따라 묶어 압축·추상화한다. 필요한 기능·의미를 보존하면서 유사한 정보·조작을 통합하고, 요구가 추가되면 기존 구조 전체를 다시 정리한다.
   - 사용자 취향(UDP-03): 선택한 기반의 구조·동작을 필요한 범위까지 재구현한 뒤 목적에 맞게 변형한다. 기반 상태를 결과와 대조할 수 있게 보존하며 별도 앱을 중복 제작할 필요는 없다.
   - 핵심 정보, 함께 비교할 정보, 필요할 때 열 보조 정보를 구분한다. 사용자 취향(UDP-06): 같은 의미와 용도의 정보는 한 화면에서 한 번만 표시하고 반복 설명·출처·주의·상태는 한 위치로 통합해 다른 위치에서 연결한다.
   - 기본·로딩·빈 상태·오류·완료·권한 제한 등 필요한 상태를 포함한다. 설계·검토만 요청받은 경우에는 해당 결과까지 수행한다.
5. **품질 검사**
   - 결과를 내기 전에 `references/quality.md`의 해당 항목을 확인한다.
   - 대표 사용 장면에서 핵심 정보를 찾아 원하는 판단·행동으로 이어갈 수 있는지 확인하고, 압축에 따른 기능·의미 손실과 반복 표시를 검사한다.
   - 선례를 활용한 결과는 가져오려던 장점에 맞는 조건·방법으로 원본과 대조한다. 의도한 변형과 장점의 의도치 않은 손실을 구별하고, 확인하지 못한 부분은 남긴다.
   - 실제 화면 작업이면 가능한 viewport에서 겹침, 잘림, 빈 화면과 상호작용을 검증한다.
   - 기존 화면을 바꿨다면 고정한 핵심 시나리오를 변경 전후에 같은 조건으로 확인한다.
6. **피드백 학습**
   - 사용자가 반복 적용할 피드백을 주면 `references/feedback.md`로 판단 구조를 추출한다.
   - 일회성 취향이나 구현 사고를 보편 원칙으로 승격하지 않는다.
   - 현재 화면의 피드백 반영과 지속 원칙 저장을 구분한다. 승격할 만한 근거는 후보로 제안하고, 사용자가 지속 원칙으로 확정한 범위에서만 `references/user-principles.md`를 갱신한다. 이미 확정·승인한 같은 범위는 다시 묻지 않는다.

## 구현 인계

실제 화면을 구현해야 하면 `my-design`은 대상 화면, 사용자 판단 질문, 핵심 행동, 압축한 정보 구조, 필요한 상태, 변경 금지 영역과 완료 검사를 구현 Skill에 넘긴다. 선례를 활용하면 사용자가 선택한 원본 화면·근거, 가져올 구조·동작, 필요한 변경과 이유, 기반 상태의 보존·대조 방법을 함께 넘긴다. 구현 뒤에는 결과 화면을 다시 확인하고 `references/quality.md`로 선례 대조·판단·중복 표시·상호작용과 기존 기능 회귀를 검사한다.

작은 구현 수정을 별도 실행 단위로 떼어낼 때는 기존 화면의 사용자 의도·정보 구조·주요 상태가 유지되고, 정확한 대상 작업공간과 좁은 write set, 완료 기준과 실행할 build·기능 test가 사전에 고정돼 있어야 한다. 새 의존성·넓은 refactor·파일 위치 탐색·새로운 시각 판단이 필요해지면 작은 수정으로 취급하지 않고 R4에서 위임 범위와 계획을 다시 검토한다.

위임 시 절대경로의 대상 작업공간, 허용 파일, 화면 계약과 검증 명령을 전달한다. 다른 작업이나 작업공간의 persisted/resume session을 재사용하지 않는다. 원 작업은 최종 기능·반응형·시각 검증을 소유한다. 명백한 실패는 관찰 사실과 원인 가정을 구분해 같은 정확한 작업공간의 새 실행에서 보정한다. 비용을 통제하면서 유효한 보정을 허용하기 위해 횟수보다 R5의 근거·비용·권한 기준으로 재시도를 판단한다. 다음 시도가 원인을 구별하거나 새 증거를 만들고 계약의 범위·완료 기준·권한·복구 조건을 유지할 때 이어간다. 같은 가정의 반복, 불분명한 추가 자원 가치, 계약 변경 또는 실행 불가는 상태와 대안을 알릴 지점이며 다른 모델·경로로 조용히 전환하지 않는다. 모델·추론 설정은 별도로 지정하지 않고 메인 작업의 설정을 계승한다.

도구별 호출법은 이 Skill에 복사하지 않는다. `my-design`은 무엇을 만들고 어떻게 판단할지만 소유한다.

## 출력

요청 크기에 맞춰 다음 중 필요한 것만 제공한다.

- 화면 또는 구현 결과
- 우선순위가 있는 개선안
- 근거와 신뢰도
- 확인한 상태와 남은 위험
- 새로 확인된 사용자 디자인 원칙 후보

활용한 선례의 근거와 적용·변경 이유, 결과 대조와 남은 미확인을 이번 작업에 연결해 설명한다. 회사별 영구 디자인 사전으로 확대하지 않는다.

## 참고 문서 선택

- 설계·검토 기본 원칙: `references/principles.md`
- 확정된 사용자 고유 원칙: `references/user-principles.md`
- 외부 사례와 실험 근거가 필요함: `references/research.md`
- 사용자 피드백을 재사용 자산으로 만듦: `references/feedback.md`
- 완료 전 품질 확인: `references/quality.md`
