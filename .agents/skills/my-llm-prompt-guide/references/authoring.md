# Skill·워크플로우 작성·수정 기준

Skill·워크플로우 지침을 작성·수정할 때 읽는다. 공식 `skill-creator`의 기술 형식·도구·검사 절차를 복제하지 않고 사용자 고유 기준을 보완한다.

## 의도와 라벨

기존 Skill의 전수·소급 라벨링은 하지 않는다. 현재 지침은 기본 책임으로 취급하고, 앞으로 새로 작성하거나 수정하는 부분에서 작성 의도와 아래 구분을 확인한다. 기본 책임은 기본값이므로 라벨을 반복하지 않는다. 확인된 사용자 취향이나 실제로 필요한 모델 보완에만 관련 문장 또는 묶음 가까이 표시한다.

| 구분 | 남길 내용 | 재검토 시점 |
|---|---|---|
| 기본 책임(기본값) | 해당 자산의 목적·역할과 지침이 필요한 이유 | 목적·역할·작동 조건이 달라질 때 |
| 사용자 취향 | 확인된 선호·이유와 적용 범위 | 사용자가 선호를 바꾸거나 적용 범위가 달라질 때 |
| 모델 보완 | 확인된 모델·버전, 부족함의 근거, 보완 목적 | 모델 변경 또는 새 수행 근거가 생길 때 |

사용자는 기존 Skill을 모델 보완 사항을 최대한 넣지 않는 방향으로 작성했다고 설명했다. 따라서 기존 일반 지침이나 교정 피드백을 모델 성능 보완으로 재해석하지 않는다. 신규·수정 시에도 모델 보완 지침의 추가는 최소화한다. 확인된 대상 모델·버전의 부족함과 보완 필요가 있을 때만 근거·재검토 조건을 남기며, 추정 원인을 모델 결함으로 확정하거나 대상 모델·버전을 만들지 않는다. 기본 책임도 수정 가능하며 모델 변경만으로 지침을 자동 삭제하지 않는다.

작성·수정 전 기존 의도와 사용자 합의를 읽고, 변경 묶음별 성격(기본 책임·사용자 취향·모델 보완)과 근거·작성 이유·적용 범위를 판단한 뒤 작성한다. 지침을 읽은 뒤 실제 작성·검사에서 빠지는 일을 줄이기 위한 실행 기준이다. 문장을 통합·분리하거나 다른 파일로 옮길 때도 해당 구분과 근거 연결을 유지한다.

지속 적용할 합의는 담당 Skill에 행동·적용 조건·제외 범위와 필요한 이유를 반영하고, 이번 세션만의 승인은 SESSION에 둔다. 수정 후 합의와 실제 문구를 대조해 누락·충돌·범위 확대가 없는지, 이미 합의한 행동의 허가를 다시 요구하지 않는지 확인한다. 미채택 제안을 확정으로 바꾸지 않는다. 유지할 목적과 변경 이유를 구분하고 중요한 이유는 관련 지침 가까이에 짧게 설명한다. 사용자 의도와 AI 해석을 구별하고, 의도가 미확인이면 그렇게 표시한다. 현재 설명을 갱신하고 같은 첨언·날짜별 로그를 본문에 누적하지 않는다.

## 파일 구조

기술 형식은 공식 `skill-creator`를 따른다. 파일별 역할은 다음처럼 맞추되, 실제 필요한 파일만 사용한다.

설치 위치 — 사용자 선택: 이 워크플로우에서 직접 관리하는 개인 Skill의 개발 원본은 `source/skills/<skill-name>`, 설치본은 사용자 홈의 `.agents/skills/<skill-name>`에 둔다. 설치 위치가 분산되어 누락·중복으로 오판하지 않도록 새 생성·갱신에서도 이 위치를 명시하며, 도구의 기본 설치 경로가 달라도 그대로 따르지 않는다. Codex 내장·공식·외부 플러그인 자산은 각 도구의 관리 위치를 유지한다.

- `SKILL.md`: 목적·작성 이유, 적용 범위·책임, 공통 행동, 조건별 참조와 읽을 시점.
- `references/`: 특정 조건의 상세 기준·절차·예시. 본문과 중복 저장하지 않는다.
- `scripts/`: 반복 또는 결정론적 처리. 입력·출력·실패 조건을 확인할 수 있게 한다.
- `agents/openai.yaml`: 본문과 일치하는 표시·호출 설정.
- `assets/`: 산출물에 쓰는 자료와 필요한 사용 조건.

단순한 Skill에 빈 구획·파일을 만들지 않는다. 구조 통일 때문에 전문 Skill의 고유 기능을 제거하지 않는다.

## 개인 Skill 제작 배경 — 사용자 선택

새 개인 Skill을 만들 때 [제작 배경 기록](design-context-template.md)에 따라 `references/design-context.md`에 만든 니즈·참고 기반·작동 방식·주의점을 기록한다. 제작 당시 확인한 이유와 개념을 보존하고 조회 사이트에서 읽기 위한 문서이며 실행 지침을 복제하지 않는다. `scripts/init-design-context.mjs`는 원문 해시가 붙은 초안을 만들고 기존 문서를 보존한다. 내용을 작성한 뒤 확인된 범위에서 상태를 정하며, 현재 원문과의 대응을 함께 갱신한다.

기존 스킬의 제작 배경·분야를 일괄 소급 라벨링하지 않는다. 기존 자산은 시각화를 다듬은 뒤 사용자가 하나씩 라벨링한다. 참고 기반을 입력 자료와 혼동하거나 미확인 개념을 추정해 채우지 않는다. 개발 원본과 승인된 설치본에 같은 문서를 연결하며 사이트는 GitHub 판본을 읽는다. 문서가 없거나 미확인 상태여도 스킬 조회·사용을 막지 않는다.

## 품질 게이트

아래 사항 중 변경에 관련된 것을 실제 근거로 확인하고, 충족·미충족·미확인을 구분한다.

1. 사용자 입력·원하는 변화와 지침의 연결, 기존 목적과 변경 이유가 설명되는가?
2. 호출 조건·범위·책임이 명확하고 기존 권한을 보존하는가?
3. 본문·참조·메타데이터가 일치하고 필요한 상세로 연결되는가?
4. 최종 변경분을 작성 전 분류와 대조해 라벨 누락·오분류가 없고 근거·적용 범위·재검토 조건이 맞는지 확인했는가? 기본 책임의 무표시는 정상으로 구분했는가?
5. 일반 설명·중복·불필요한 제한을 줄이면서 중요한 기능과 이유를 보존했는가?
6. 바뀐 지침이 실제로 어떤 행동을 개선하는지 설명할 수 있는가?

공식 형식 검사와 변경에 필요한 동작 확인을 수행한다. 스크립트·깨지기 쉬운 연결·중요 판단은 관련 확인을 하되, 문구·구획 존재만으로 행동 품질을 통과시키지 않는다. 기술 검토는 AI가 맡고 사용자 목적·취향·중요 선택의 변화는 유효한 판단 경계를 따른다. 이미 합의한 의도를 반복 승인받지 않는다.

설치·반영 전에 최종 변경분의 의도·라벨 대조를 마치고, 그 판단 근거를 형식·참조·해시 등의 기술 검사 결과와 구분해 남긴다. 필요한 의미 검토가 미완료인 부분은 보완 후 반영한다. 검토한 판본에서 문장이 다시 바뀌면 영향받은 부분을 재검토한다. 라벨 키워드의 존재만으로 분류의 정확성을 판정하지 않는다.

이 게이트는 작성·수정 산출물을 확인한다. 수행한 작업의 원하는 변화 달성과 Plan·Prompt·Probe·Protect·Technique·Intent·Cognition 평가는 별도로 해당 작업 근거로 판단한다. 형식 검사·설치·호출을 실사용 효과로 간주하지 않는다.
